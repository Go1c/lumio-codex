# Live QA Acceptance（线上验收）

以 QA 身份在**线上环境**实测：按 bug 单复现问题、给出判定、把结论与证据回写进 Workflow。核心纪律：**结论只来自线上实测**——读代码、看提交记录只能辅助定位复现路径，不得代替实测下结论。

## 何时使用

- 用户指派核实某张 Workflow bug 单（B- 单号）：评估问题是否真实存在。
- 缺陷修复上线后复测（回归验收）。
- 新功能上线后验收实际效果。
- 围绕某功能面做探索性测试，找新 bug。

## 硬边界（生产环境红线）

- **验收结论只认线上**：Web 在 `https://bestcodex.app/`（账号面延伸到门户 `lumiogame.com` 与 `api.lumio.games`），桌面在本机安装的 BestCodex APP。本地 / dev 环境的表现不得作为线上验收结论。
- **只用用户提供的测试账号**；缺账号 / 缺权限 / 缺前置数据 → 判「阻塞」并停下问用户，不批量注册账号、不动真实用户数据。
- **不触发真实扣费**：支付 / 充值链路只验到下单确认页为止。
- **不做破坏性操作**（删除数据、注销账号、改影响他人的设置）——除非用户明确指定可牺牲的测试账号并确认。
- 证据截图含邮箱 / token / 余额等敏感信息时，上传前先裁剪或打码；`rules/system.md` 安全条款全程适用。

## 前置条件

- 拿到验收对象：bug 单号（经 `workflow-ops` 读单并拉取截图附件），或功能点描述。
- Web 侧有可用的浏览器自动化（快照 + 截图能力）；桌面侧有可用的桌面 UI 自动化（如 `computer-use` 技能）——不可用时降级为 Web-only，并在报告中声明。

## 操作步骤

### 流程 A · Bug 单核实 / 修复复测

1. **读单**：经 `workflow-ops` 拉取 bug 单全文与截图附件；提取复现步骤、预期 vs 实际、环境信息（浏览器 / APP 版本 / 账号状态）。步骤缺失就从截图倒推（URL、页面状态、操作痕迹）。
2. **列复现脚本**：前置条件（账号、数据状态）→ 操作序列 → 观察点。前置条件凑不齐 → 判「阻塞」。
3. **线上复现**：逐步执行，**每个关键步骤截图**；到达观察点后与单内截图逐项对照（元素、文案、数据、布局）。
4. **变体重试**（首次未复现时必做）：换单内提到的环境（浏览器 / 语言 / 视口 / 账号状态），重复操作时序至少 2 次；把尝试过的变体记入证据。
5. **判定**：按「判定口径」取值。
6. **回写**：经 `workflow-ops` 上传证据截图为附件、按模板发评论、现查 transitions 后流转状态；其硬闸门全部适用（读回验证、不猜自定义字段值）。
7. **交付**：向用户报判定 + 单链接 + 证据摘要。

### 流程 B · 探索性测试（找新 bug）

1. 圈定功能面：用户指定，或验收单的相邻链路。
2. 沿主链路走一遍正常流，再打边界：空输入 / 超长输入 / 快速重复操作 / 刷新与回退 / 未登录直达深链 / 窄视口。
3. 发现疑似问题 → 先截图固定证据 → 再重复一次确认可复现。
4. **建单前先经 `workflow-ops` 查重**；新 bug 单必须先报给用户、确认后落单——探索所得不在原验收指派的授权范围内。

### 双端交叉（Web + 桌面 APP）

bug 涉及账号、登录、余额、充值、同步等跨端功能时，同一测试账号在 Web 与桌面 APP 各验一遍，差异写入评论——「仅 Web 复现 / 仅 APP 复现 / 双端复现」是重要定位信息。

## 判定口径

| 判定 | 含义 |
|------|------|
| 属实 | 线上按步骤稳定复现，与单内描述一致 |
| 部分属实 | 现象存在但与描述有出入（触发条件 / 表现范围不同），差异写清 |
| 无法复现 | 含变体重试仍未出现；≠ bug 不存在，评论列出全部已尝试变体 |
| 已修复 | 复测原步骤不再出现，且相邻链路无新问题 |
| 未修复 | 复测仍可复现，附新证据 |
| 阻塞 | 缺账号 / 数据 / 权限，无法实测；写明缺什么 |

## 回写评论模板

```
## 线上验收：<判定>
- 环境：<URL 或 APP 版本> · <时间> · <浏览器 / 系统>
- 账号：<测试账号标识，脱敏>
- 步骤：1. … 2. … 3. …
- 实际观察：<看到什么，与单内描述 / 截图的异同>
- 已尝试变体：<仅「无法复现」时必填>
- 证据：<附件文件名列表>
```

## 注意事项（Pitfalls）

- **看代码下结论**是本技能头号反模式——代码「应该没问题」不是验收结论，线上跑一遍才是。
- 截图是判定的必要条件：没有截图的步骤等于没做。
- 「无法复现」最容易草率：环境没对齐（账号状态、缓存、语言）就下结论，会把真 bug 关掉。
- 线上有真实用户：探索测试的写操作控制在测试账号自身数据内，测完能清则清。
- 回写规矩不在本技能里重复——`workflow-ops` 的闸门是单一权威，冲突以它为准。

## 验证

- [ ] 判定有截图证据支撑，且证据已作为附件回传到 bug 单。
- [ ] 评论按模板落单，状态流转经现查 transitions 执行并读回验证。
- [ ] 「无法复现」时已完成变体重试并逐条记录。
- [ ] 全程未触发真实扣费、未动真实用户数据。
- [ ] 向用户交付：判定 + 单链接 + 证据摘要 + known gaps（如仅单端验证）。
