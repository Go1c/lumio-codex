# M4 规范缺口与取舍记录

记录实现 `apps/admin` 期间发现的规范矛盾、歧义与前端的临时判断。
**未修改** `docs/design/interaction-design.md` 与 `design/prototype/`，全部留待评审决策。

真源优先级：交互设计文档 > 原型（视觉与文案）> `services/cchaven-control` 代码（接口以代码为准）。

---

## 1. 「已禁用」被混进订阅状态筛选维度

- **现象**：7.2 与原型把筛选 chips 定义成「全部 / 已订阅 / 试用中 / 未订阅 / 已禁用」，
  但「已禁用」是账号状态，「已订阅 / 试用中 / 未订阅」是订阅状态——一个被禁用的用户仍可能在订阅期内。
- **后端现状**：`store.ListAdminUsers` 把两者压成单一 `sub_state`，`disabled` 优先级最高
  （`CASE WHEN u.status = 'disabled' THEN 'banned' ...`），并在注释里写明了这是与原型视觉对齐的选择。
  `docs/m1-spec.md` 第 4.4 条也记录了同一判断。
- **本次实现**：沿用后端的单一 `status` 维度，视觉与原型一致。被禁用用户的订阅状态在列表中不可见。
- **建议**：后续评审拆成两个筛选维度（账号状态 × 订阅状态），或在行内同时展示两个徽标。

## 2. 用户详情页缺接口，「详情页二次权限」无法落地 —— ✅ 已解决

- **现象**：7.5 要求「用户敏感信息（邮箱）在列表中打码显示，详情页需二次权限」，
  `docs/m1-spec.md` 2.8 也列了 `GET /users/{id}`。
- **当时的后端现状**：`internal/api/api.go` 的 `/api/admin/v1` 路由表里**没有**该路由，服务层也没有对应方法。
- **当时的实现**：只做列表，邮箱始终是后端下发的 `email_masked`，前端从不持有明文，因此也没有详情页入口。
- **解决方式**：后端补上了 `GET /api/admin/v1/users/{id}`（`service.UserDetail`），
  路径参数是数字主键，返回 `{user, entitlement, devices, referral, orders}`，
  其中 `user.email` 是明文；`CanViewUserDetail` 只放行 `owner` / `ops`，
  且成功与被拒两条路径都写审计（`user.view_detail` / `user.view_detail_denied`）。
  前端据此补了 `/users/:userId` 详情页：用户列表行操作列新增「详情」按钮（support 为禁用态并在工具栏下方说明原因），
  页面顶部常驻一条提示「本页展示明文邮箱，属于二次权限范围；每次访问都会记入审计日志」，
  邀请进度里被邀请者的邮箱仍是打码值。403 就地渲染，不把整屏踢回登录页——会话本身没有问题。
- **遗留**：后端的权限口径（support 不放行）是我们自行取的最小可辩护解释，交互设计 7.5 仍未给出权限矩阵。
  这条口径后来被扩展成了完整矩阵（support 全线只读），见「待决策 4」。

## 3. 审计日志在信息架构里没有位置

- **现象**：7 章明确「四个页面」，但 7.5 要求留操作审计日志，规范没说这些日志在哪看；任务书也让我自行判断。
- **本次实现**：作为**运营配置页的子区块**（页面底部「操作审计日志」，分页 10 条/页）。
  理由：侧栏仍是规范里的四个入口，不擅自新增第五个页面；审计与「谁改了什么配置」高度相关，放一起阅读成本最低。
- **代价**：审计日志同时覆盖用户禁用与订单退款，放在配置页下并不完全贴切；
  日志量大以后需要按操作人/动作/时间筛选，届时更适合独立页面。
- **筛选缺失部分 ✅ 已解决**：`store.ListAuditLogs` 已支持 `?actor=`（管理员数字 ID，精确匹配）
  与 `?action=`（动作枚举，精确匹配），空串表示不筛选、两者可组合。
  前端在审计区块加了「操作人 ID」输入框（300ms 防抖）与「动作」下拉，附「清除筛选」；
  筛选后无结果显示「没有匹配的审计记录。」，与未筛选时的空态区分开。
- **仍待决策**：是否升格为第五个页面（时间范围筛选也还没有）。

## 4. 「今日收入」与「今日汇总」的口径未写明

- **现象**：7.1 的收入卡与 7.3 的页头汇总都叫「今日」，规范没说是否同源、是否只算已支付。
- **后端现状**：两者都来自 `store.TodayOrderSummary(today, tomorrow)`，即同一口径。
- **本次实现**：仪表盘收入卡与订单页汇总用同一份数字（mock 里也刻意从同一份订单派生），金额单位由分转元。
- **建议**：明确「今日」是服务端本地时区的自然日，且退款不回冲当日收入（当前后端就是这个行为）。

## 5. 退款终态取决于渠道，规范只描述了理想流转

- **现象**：7.3 写「二次确认 → 状态转「退款中」→ 完成后转「已退款」」，像是必然两段式。
- **后端现状**：`RefundOrder` 同步调用支付渠道，渠道即时成功就直接落 `refunded` 并返回该状态，
  否则停在 `refunding`；没有轮询接口，也没有 webhook 之外的完成通知。
- **本次实现**：确认后先把行乐观置为「退款中」并 toast「退款已发起…」，再按响应里的 `status` 落终态：
  `refunded` → toast「退款完成」；`refunding` → toast「退款处理中，稍后自动转为已退款」，需要用户手动刷新才能看到终态。
- **建议**：要么补一个订单状态轮询/订阅接口，要么在规范里承认「退款中」是需要刷新的中间态。

## 6. 订单表「时间」列的语义

- **现象**：7.3 写「支付时间」，但支付失败的订单没有支付时间（后端 `paid_at` 为 `null`）。
- **本次实现**：列名保持「支付时间」，`paid_at` 为空时回落展示 `created_at`（下单时间），不留空格子。
- **建议**：改成「时间」，或拆成「下单时间 / 支付时间」两列。

## 7. 支付渠道 `mock` 通道会出现在真实数据里

- **现象**：7.3 的渠道枚举只有支付宝 / 微信支付 / 银行卡，但 `domain.ChannelMock` 是 M1 就有的真实取值。
- **本次实现**：额外映射为「测试通道」，未知取值原样展示，避免出现空白单元格。
- **建议**：确认生产环境是否会写入 `mock` 渠道；若会，规范里补上这个枚举。

## 8. 「注册来源」的本地化位置不一致

- **现象**：7.2 要求来源显示为「自然流量 / 邀请（含邀请者 ID）/ 其他渠道」。
- **后端现状**：`service.sourceLabel` 已经把来源本地化成中文，但邀请者 ID 是单独的 `inviter_id` 字段。
- **本次实现**：有 `inviter_id` 时用前端模板拼成「邀请（U-100986）」，否则直接展示后端下发的 `source`。
  这意味着来源文案的语言由后端决定，切 zh-HK 时这一列不会跟着切。
- **建议**：后端改为下发枚举值（`organic` / `invite` / `other`）由前端本地化，或明确接受后端下发文案。

## 9. 分布图的百分比由前端计算

- **现象**：7.1 的分布图是「横向占比条」，但后端 `store.Bucket` 只给 `{label, count}`。
- **本次实现**：前端按各段 count 求和后算百分比并四舍五入，因此各段之和可能是 99% 或 101%。
- **建议**：可接受；若要求严格 100%，需后端下发百分比或前端做最大余额法分配。

## 10. APP 版本分布缺「最新版」标记

- **现象**：原型把版本标成「1.4.2（最新）」，用于评估强制升级时机。
- **后端现状**：`AppVersionDistribution` 只返回原始版本号，没有「哪个是最新」的信息。
- **本次实现**：只展示版本号，不标「最新」。
- **建议**：分布接口带上当前发布版本（`app_releases.is_current` 已有该数据），或前端另取一次发布信息。

## 11. 后台没有规定分页与「共 N 条」的展示

- **现象**：7 章没提分页，原型是一页平铺的演示数据；但后端所有列表接口都是分页的。
- **本次实现**：用户 / 订单每页 20 条，审计日志每页 10 条，底部给「第 x / y 页 · 共 n 条」与上一页/下一页。
- **建议**：评审确认页大小与是否需要跳页。

## 12. 「最近活跃」的时间粒度

- **现象**：原型用「刚刚 / 13 分钟前 / 昨天 / 3 天前」，6.5 规定日期格式是 `YYYY年M月D日`。
- **本次实现**：30 天内用相对时间（与原型一致），超过 30 天回落 `YYYY年M月D日`；
  表格里的注册时间、支付时间用 `YYYY-MM-DD HH:mm`（与原型一致），确认弹窗与正文用 6.5 的格式。
- **建议**：在 6.5 里补一句「表格内时间可用紧凑格式」，免得后续被判为不符规范。

## 13. 管理端错误文案未覆盖「会话过期」的前端呈现

- **现象**：6.2 规定会话过期文案「登录已过期，请重新登录。」，但后台侧没写在哪展示。
- **本次实现**：任何 `401`（非 `mfa_required`）都会把整屏退回登录页，后端文案通过下一次提交时的错误条呈现；
  退回瞬间不额外弹 toast，避免与登录页错误条重复。
- **建议**：确认是否需要在退回登录页时主动提示「登录已过期」。

## 14. 用户「展示号」与「主键」曾经混用

- **现象**：用户列表行早期只下发展示号 `id`（`U-100986`），而禁用/解禁接口的路径参数是数字主键。
- **当时的实现**：前端用 `id.replace(/^U-/, "")` 取出数字再拼 URL。
  这个写法当时能跑通，但它把「展示号 = `U-` + 主键」这条后端的呈现约定，变成了前端的解析责任——
  展示号格式一旦调整（补零、换前缀、改成与主键无关的注册号），前端会安静地发出错误的 ID。
- **解决方式**：后端在列表行与详情的 user 对象里同时下发了 `user_id`（int64）。
  前端所有接口调用（详情、禁用、解禁）一律用 `user_id`，`id` 只进 UI 不进 URL；
  `numericUserID` 这个反解函数已删除。MSW mock 的路径参数改为严格数字校验（对齐后端 `strconv.ParseInt`），
  收到展示号直接 400，配合 `users.test.tsx` 里断言真实请求路径的用例，防止这类写法回归。
- **建议**：其它「展示值 / 主键」并存的字段（如订单号 vs 订单 ID）沿用同一约定：
  凡是要回传给后端的标识，后端都显式下发，不让前端从展示值反推。

   已解决，见第 3 条；仍缺时间范围筛选。
4. **管理员角色权限矩阵：倒挂已修复，口径仍待产品确认**。
   - **原问题**：只有「用户详情（明文邮箱）」按角色区分，其余写操作三种角色一视同仁。
     于是 support **不能看**用户邮箱（只读），却**可以禁用**该用户、发起退款、改包月价格——
     破坏性操作的门槛低于读取敏感信息，比完全没有角色更危险，因为它看起来像是受控的。
   - **已实现的矩阵**（原则：破坏性操作的门槛不得低于读取敏感信息）：

     | 能力 | support | ops | owner |
     | --- | --- | --- | --- |
     | 仪表盘指标、用户列表（打码）、订单列表、审计日志、读运营配置 | ✅ | ✅ | ✅ |
     | 用户详情（明文邮箱）、禁用/解禁、退款、改运营配置、导出订单 CSV | ❌ | ✅ | ✅ |

     即 **support 全线只读**；导出 CSV 归入写操作一侧（批量把用户邮箱带出系统）。
     owner 与 ops 暂无差异是刻意的：现在没有真实差异，硬造一个只会变成要靠记忆的规则；
     保留 owner 是为将来的管理员账号管理（增删管理员、改他人角色）只给 owner。
     后端矩阵的唯一出处是 `internal/service/admin.go` 的 `roleCapabilities`，
     前端 `src/api/types.ts` 里是它的副本，只用于提前禁用入口，不承担裁决。
   - **前端呈现**：support 无权的入口一律**禁用态 + 原因说明**，说明文字用 `aria-describedby`
     关联到按钮（禁用按钮不可聚焦，tooltip 读不到）；覆盖用户页「详情 / 禁用 / 解禁」、
     订单页「导出 CSV / 退款」、配置页「保存配置」。运营配置页对 support 是**只读版本**
     （输入框 `readOnly`、值照常展示）而不是整页 403——客服要能回答「现在奖励几天、包月多少钱」。
     每个页面同时保留就地 403 兜底（直接敲 URL、或前后端矩阵不一致时），
     403 一律**不当作会话失效**：不换整屏 403 页、不退回登录页，会话本身是有效的。
   - **仍需产品确认**：(a) owner 与 ops 是否真的同权；(b) support 是否需要「可看明文邮箱但留痕」
     这类受限读取；(c) 成功导出 CSV 是否也要写审计（当前只审计被拒）；(d) 是否需要第四种角色。
5. **zh-HK 字典是空的**：结构已就位（缺条目回落 zh-CN），等文案确定后逐条补齐；界面上暂未提供语言切换入口。
